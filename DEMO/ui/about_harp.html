ICICLE · HPC scheduling

HARP · HPC Application Runtime Predictor

Before you submit a job to a supercomputer you have to say how long it will run. HARP learns that from your own application: it runs it many small ways, trains models on the timings, and predicts the time for the run you actually want.

1 · The problem

How long should you ask for?

Every HPC job request includes a time limit. Ask for too little and the scheduler stops your job before it finishes. Ask for far too much and you wait longer in the queue, and the hours you reserve sit idle while others wait. Move the slider: the run really takes 3 hours.

3 · Words you will hear

A small vocabulary

Open a card for the meaning.

SD run
scaled-down

A small, quick version of the problem: small inputs, few iterations. Cheap to run many of, so the models learn mostly from these.

FS run
full-scale

The real sizes you care about. Expensive, so only a few. Some are mixed into training (25, 50 or 75%) and some check the models while they train.

test_data run
held out

Runs kept aside and never trained on. They score the finished models honestly.

Sweep
what you set up

One app, one run type (SD, FS or test_data), and the parameter values to try, for example n = 10, 100, 1000, run on the queues you tick.

Campaign
a submitted sweep

The record of a sweep once submitted: its TAPIS jobs, their status, and one results folder. The word comes from Cheetah, which version 1 uses to run sweeps. In version 2, one sweep is one campaign.

Hardware configuration
where a run happens

A system, queue, number of cores and memory, e.g. Pitzer serial with 8 cores. Profiling the same run on several configurations teaches the models how hardware changes the time.

TAPIS
the door to the clusters

An API (from TACC) for running containers as jobs on HPC systems and moving files, using your own accounts. HARP talks to OSC and TACC only through TAPIS.

Models
LR · NN · DTR

Linear regression, a small neural network and a decision tree. Each is trained on several mixes of SD and FS data, with and without padding (predictions scaled up so they are too low less often).

Allocation account
who pays for compute

The project a job is charged to, e.g. -A PAS2271. Needed to run jobs, not to move files.

4 · Version 1 and version 2

From a modular toolkit to a service

Same three phases, same models. What changes is who drives them and how much of the cluster they can use.

Version 1 · modular

a toolkit you run yourself, per user, per session

HARP is a pipeline you install as a module (OSC) or bake into a container together with your app. You drive it from a notebook: log in to TAPIS in that session, register the app, submit one job. Inside that one container, Cheetah runs every SD, FS and test sweep on one machine, then the same job builds the models and picks one.

Version 2 · service

a web page and a backend that run HARP for you

A web page (HARP Generate, Build, Estimate) and a HARP server. You log in once; the server keeps your TAPIS session, splits each sweep into many TAPIS jobs across systems, queues and hardware configurations, follows them live, merges the results, runs the build as its own TAPIS app, and lets you pick a model to estimate with.
